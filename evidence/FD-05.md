# Evidence — FD-05

- Datum: 2026-09-22
- Stav: hotovo

## Vstup

`DriverPresenceService` už používal `drivers:online` přes `SADD`/`SREM` a
samostatný heartbeat klíč s TTL 15 sekund. Redis klient přidává prefix `fd:`,
takže skutečné klíče jsou například `fd:drivers:online` a
`fd:drivers:lastseen`. Expirace heartbeat klíče sama neodstraňovala řidiče
z online Setu ani z GEO indexu.

## Očekávání

- Opakované přihlášení stejného ID nechá `SCARD` beze změny.
- Heartbeat uloží čas v milisekundách do `drivers:lastseen` a obnoví TTL.
- Bez heartbeatu `isActive` vrátí `false`, i když ID ještě zůstává v online Setu.
- Úklid odstraní staré ID z online Setu, `lastseen` a GEO indexu.
- Heartbeat mezi výběrem kandidáta a smazáním zachová obnoveného řidiče.

## Skutečný výsledek

Implementace používá `SISMEMBER` pro `isOnline`, `SCARD` pro
`getOnlineCount`, `ZADD GT` pro neklesající čas heartbeatu a
`ZRANGE BYSCORE` pro kandidáty starší než 15 sekund. Přihlášení založí první
heartbeat ještě před `SADD`, aby bylo možné uklidit i řidiče, který už další
heartbeat nepošle. Heartbeat klíč a `lastseen` se zapisují v jedné Redis
transakci. `isActive` vyžaduje členství v online Setu i platný heartbeat.

Každého kandidáta úklid zkontroluje a případně odstraní jediným Lua skriptem:
`ZSCORE` ověří aktuální čas, pak `SREM` odstraní členství a `ZREM` odstraní
záznam z `lastseen` i GEO indexu. Mezi kontrolu a odstranění se jiný Redis
příkaz nemůže vložit.

Ověření na skutečném Redis 8 proběhlo pod izolovaným prefixem
`fd:lab:fd05:<běh>:`. Před úklidem byly oba řidiči starými kandidáty;
testovací klient vložil heartbeat pro `renewed` až po `ZRANGE BYSCORE` a před
Lua kontrolou:

```json
{
  "first": true,
  "duplicate": false,
  "countBefore": 2,
  "oldCandidates": ["renewed", "stale"],
  "removed": 1,
  "countAfter": 1,
  "renewed": { "online": true, "active": true, "geo": true },
  "stale": { "online": false, "active": false, "lastSeen": null, "geo": false }
}
```

Samostatný pokus ověřil i první přihlášení: `lastseen` vznikl, řidič byl
aktivní, po simulovaném vypršení heartbeatu `isActive` vrátilo `false` a úklid
odstranil jeho ID. Pozdější heartbeat s nižším timestampem nevrátil score
zpět. Testovací klíče byly po pokusech odstraněny. Celá sada testů (63/63),
TypeScript typecheck a ESLint prošly.

## Chybový pokus

Na izolovaných testovacích klíčích jsem vyzkoušel naivní postup: načíst staré
ID pomocí `ZRANGE BYSCORE`, obnovit mu `lastseen` a přesto smazat dříve
načtené ID příkazem `SREM` bez nové kontroly:

```json
{ "candidates": ["renewed"], "onlineAfterNaiveCleanup": 0, "freshScoreStillPresent": true }
```

Řidič měl nový timestamp, ale zmizel z online Setu. To je chybný stav,
kterému Lua kontrola brání.

## Odpověď na kontrolní otázku

Výsledek starého `ZRANGE BYSCORE` je jen snímek. Řidič může mezitím poslat
heartbeat, který přesune jeho score mimo interval zastaralých řidičů. Smazání
podle původního seznamu by odstranilo právě obnovené ID. Proto úklid čte
aktuální `ZSCORE` a případné odstranění provede atomicky.

## Podmínky splnění

- [x] Duplicitní online přihlášení nezvýší počet řidičů.
- [x] Řidič bez heartbeat není přes `isActive` nabízen jako aktivní.
- [x] Závod mezi výběrem kandidáta a jeho smazáním neodstraní obnoveného řidiče.

V projektu zatím není endpoint pro nabídku řidičů ani periodický spouštěč
úklidu. Dostupnost se proto musí vyhodnocovat přes `isActive` a
`cleanupStaleDrivers` musí volat aplikace nebo plánovač při začlenění
vyhledávání řidičů.
